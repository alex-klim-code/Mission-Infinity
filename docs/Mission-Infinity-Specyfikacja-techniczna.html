1. Charakterystyka produktu

Mission: Infinity jest przeglądarkową grą edukacyjną o planowaniu i realizacji misji kosmicznych. Obsługuje rozgrywkę solo i współpracę załogi liczącej do czterech graczy. Aktualnie rozbudowaną misją jest LUNA — Lunar Sample Return, obejmująca przygotowanie rakiety, lot na Księżyc, badania i powrót na Ziemię.

  • Interfejs gry jest w języku angielskim, w stylistyce Asterion Aerospace.
  • Lider zatwierdza kluczowe przejścia i wspólne zakupy; pozostali gracze mogą proponować wybory.
  • Profile, postacie, stan misji i historia czatu są przechowywane po stronie serwera.
  • Gra działa w przeglądarce. Nie wymaga instalacji aplikacji natywnej.

2. Architektura systemu

Projekt ma strukturę monorepo pnpm: aplikacja webowa, serwer API oraz współdzielone pakiety TypeScript znajdują się w jednym repozytorium.

Przeglądarka gracza
  React + TypeScript + Vite
        │
        ├── HTTP / REST ──► Express + Clerk ──► Fastify / API gry
        │                                           │
        └── Socket.IO ◄──────────────────────────────┤
                                                    ├── Kysely + pg ──► PostgreSQL
                                                    └── App Storage ──► pliki

Współdzielone pakiety:
OpenAPI → Orval → klient React Query + schematy Zod
mission-physics → wspólne obliczenia rozgrywki

Express i Fastify nie są dwoma niezależnymi serwerami biznesowymi. Express stanowi warstwę wejściową HTTP i uwierzytelniania, a Fastify obsługuje endpointy gry w tym samym backendzie.

Stan gry jest autorytatywnie zatwierdzany na serwerze. Animacje i lokalne podglądy nie zastępują walidacji zakupu, budżetu ani uprawnień lidera.

Konfiguracja postaci obejmuje wygląd, wiek, kraj i nazwę gracza. Awatary wbudowanego kreatora mają wspólny motyw munduru Asterion Aerospace oraz flagę wybranego kraju. Podgląd 3D wykorzystuje GLTFLoader i obsługę modeli GLB; kod zawiera również dekoder Meshopt.

Sceny misji łączą ilustracje, obrazy rakiet, elementy SVG i animacje React. Uwzględniane są ustawienia ograniczenia animacji.

Kontrakt API

OpenAPI jest źródłem definicji kontraktu HTTP. Generator Orval tworzy klienta API, hooki React Query oraz schematy walidacji. Pozwala to utrzymywać zgodność nazw pól i typów pomiędzy frontendem a backendem.

  • /api/game/me — konto i postać bieżącego gracza.
  • /api/game/catalog — katalog misji i wyposażenia.
  • /api/game/sessions/:id — aktualny stan konkretnej sesji.
  • /api/game/sessions/:id/actions — zatwierdzane przez serwer działania gracza.
  • /api/game/sessions/:id/messages — wysyłanie i odczyt historii czatu.
  • /api/socket.io — komunikacja realtime, odrębna od endpointów REST.

Logowanie obsługuje Clerk z zewnętrznymi dostawcami tożsamości. Interfejs ma wspólny ekran wejścia dla nowych i istniejących użytkowników; widoczność Google i Apple zależy także od konfiguracji dostawców w Clerk. Sam kod interfejsu nie potwierdza aktywnej konfiguracji OAuth w środowisku produkcyjnym.

7. Logika misji i obliczenia

Logika domenowa jest napisana w TypeScript. Wspólny pakiet @workspace/mission-physics udostępnia obliczenia wykorzystywane przez klienta i serwer.

  • Rocket Builder: siedem sekcji, 28 kategorii, trzy zachowane obudowy i katalog podzespołów. Zakupy uwzględniają budżet oraz wcześniej opłacone elementy.
  • Scientific Instruments: wyposażenie wymagane i opcjonalne, masa ładunku, punktacja naukowa oraz zaliczanie odpowiedniego wyposażenia z wcześniejszego etapu.
  • Tankowanie: ilość kupionego i załadowanego paliwa, cena, koszt oraz kontrola postępu napełniania.
  • Budowa, lot i lądowanie: etapy zapisywane na serwerze, animacje telemetryczne, sterowanie i kontrole sprzętu.
  • Ryzyko: jakość części wpływa na model uszkodzeń; uwzględniane są zdarzenia pogodowe, naprawy i ograniczenia powrotu.
  • Finanse: wspólne zakupy oraz mechanizm wniosków o dodatkowy budżet misji.
  • Raport: wynik misji, zrealizowane cele i rezultaty naukowe.

Dynamiczny ładunek

Pojemność ładunkowa nie jest stałym limitem. Aktualna implementacja wylicza ją jako uproszczony model oparty na jakości konfiguracji, masie sprzętu, paliwie i potrzebach lotu na Księżyc oraz powrotu. Interfejs prezentuje m.in. maksymalny i bieżący ładunek, zapas pojemności, całkowitą masę, TWR i delta-v.

To model rozgrywki, a nie certyfikowana analiza rzeczywistej rakiety. Parametry zastępcze modelu nie powinny być przedstawiane jako dane producenta części.

DEMO i pominięcie wstępu

DEMO jest osobistym ustawieniem podpowiedzi. Przycisk Build recommended rocket pozwala liderowi kupić i ukończyć zalecany projekt etapu 1 jednym działaniem, bez darmowych środków i bez podwójnego naliczania zakupów. Instrumenty naukowe i paliwo pozostają osobnymi etapami. Skip Introduction przenosi lidera z Graduation Day do Start Mission; nie uruchamia samodzielnie misji ani nie zastępuje gotowości załogi.

8. Bezpieczeństwo i niezawodność

  • Serwer sprawdza uwierzytelnienie, członkostwo w sesji i uprawnienia lidera.
  • Dane żądań i odpowiedzi są walidowane schematami Zod.
  • Wrażliwe przejścia i zakupy korzystają z transakcji oraz blokad rekordu sesji, aby ograniczyć wyścigi i podwójne naliczanie.
  • Kontrola oczekiwanego etapu zapobiega niezamierzonemu pomijaniu scen przy powtórzeniu polecenia.
  • Obecne są kontrole pochodzenia żądań oraz limity przypisane do uwierzytelnionego użytkownika.
  • Stan już wczytanej misji i konta jest zachowywany przy przejściowym błędzie sieci lub ograniczeniu 429. Użytkownik widzi komunikat o opóźnieniu aktualizacji.
  • Ponawianie uwzględnia nagłówek Retry-After. Odmowa dostępu nie jest traktowana jak zwykła przerwa sieciowa.
  • Zdarzenia realtime są grupowane: nie wywołują już odczytu profilu przy każdym tyknięciu lotu.

9. Narzędzia programistyczne i weryfikacja

  • pnpm 10.26.1 w sprawdzonym środowisku — zarządzanie monorepo i zależnościami.
  • TypeScript / tsc — kontrola typów i zależności pomiędzy pakietami.
  • esbuild — budowanie serwera API.
  • tsx i node:test — uruchamianie testów jednostkowych i domenowych w TypeScript.
  • Testy PostgreSQL — weryfikacja transakcji, uprawnień, zakupów i przejść pomiędzy etapami na danych testowych.
  • Testy przeglądarkowe Playwright — wykorzystywane do sprawdzania wybranych przepływów interfejsu, także po zalogowaniu. Nie oznacza to automatycznego pokrycia każdego ekranu.

Ograniczenia aktualnej architektury

  • Obecność graczy, powiadomienia Socket.IO i liczniki ograniczenia żądań korzystają ze stanu procesu. Obsługa wielu równoległych instancji API wymaga wspólnego adaptera i współdzielonego przechowywania tych danych.
  • Dane logowania dostawców OAuth są konfiguracją środowiska, a nie treścią repozytorium. Nie zostały w tym dokumencie ujawnione ani potwierdzone dla produkcji.
  • Nie każdy zainstalowany pakiet reprezentuje aktywną funkcję produktu. Dotyczy to w szczególności pozostawionego SDK Avaturn oraz pomocniczych komponentów UI.
